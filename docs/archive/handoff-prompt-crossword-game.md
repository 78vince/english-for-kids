# Handoff：遊戲室第二款遊戲——填字遊戲（Crossword，客廳/居家空間打樣）

## 背景

使用者參考一張截圖（客廳家具主題的填字遊戲：題目區網格交疊排列、字母拖曳區、底部中文提示），提出新遊戲企劃：填字遊戲，拖曳字母到空格作答，答對留下、答錯彈回字母區，要有關卡機制跟最高紀錄，視覺走粉色系＋裝飾小插圖。這是**遊戲室的第二款遊戲**，跟第一款翻牌配對一樣走「獨立 iframe 頁面＋`gameBridge.ts` 橋接」的架構（見 `docs/handoff-prompt-memory-match-iframe-migration.md`），但這次**從一開始就照這個架構做**，不用像翻牌配對一樣事後遷移。

## 關於「單字範圍」的設計決策（使用者已確認）

原始需求第 1 點希望「以使用者學習過的內容為主」。評估後發現：**即時依照『這個使用者實際學過哪些單字』動態生成填字網格不可行**——填字遊戲需要挑出一組彼此字母有交疊的單字才能排成網格，這種「剛好交疊得起來」的字詞組合高度依賴運氣，小朋友學過的字太少或太分散時，很可能湊不出任何一組能排版的網格。

**採用替代方案（已跟使用者確認）**：改成「以主題為單位」事先設計好的固定關卡，而不是逐使用者動態生成。單字仍然是內容庫既有的詞彙（延續「學習過的內容」精神），只是關卡本身是預先排版好、對所有使用者一致的內容，不會因人而異。

網格排版是我用一支簡單的回溯演算法（隨機挑選字母有交疊的單字、逐一嵌入網格、確認交疊處字母一致）離線算出來的，**已經直接完成第一個打樣關卡的內容**，不需要 App 端自己再寫排版邏輯或另外想單字組合。

## 已完成的內容（content 端，我已直接建立好）

- `content/schema/crossword.schema.json`：填字關卡的資料格式定義。
- `content/crosswords/houses_apartments_living_space.json`：第一個打樣關卡，主題「居家空間」（`houses_apartments`），6 個單字（BED／FLOOR／ROOF／DOOR／SOFA／ROOM，全部都是這個主題既有的正式單字，附 `vocabId` 可回溯），5×5 網格，已經用程式驗證過所有交疊處字母一致、沒有衝突：

```
BFR..
ELO..
DOOR.
SOFA.
.ROOM
```

（`.` 代表空白格，不算在網格內；字母代表每個座標的正確答案）

App 端只要照這份 JSON 的 `row`／`col`／`direction` 把每個單字鋪到網格上，就能重建出上面這個排版，不用自己再處理交疊邏輯。之後如果要擴充更多主題/關卡，我會比照這個格式繼續產出，App 端不用碰排版演算法。

## 畫面四個區塊（對應使用者截圖的需求）

1. **題目區**：網格本身。每個屬於某個單字的格子，依照「這一關要不要當作空格」分成兩種顯示：已知格（直接顯示正確字母，玩家不能動）跟空格（顯示空白，等待拖曳字母進來）。周圍加裝飾小插圖（沿用現有情境插畫的水彩/水粉風格，這次換成粉色系配色，主題呼應「居家空間」——例如檯燈、書、窗簾之類的小裝飾圖，不是每個單字都要配一張圖，純粹版面裝飾）。
2. **答題格**：題目區網格裡的「空格」本身就是答題格，不用另外做成分開的區塊。
3. **字母區**：一排散落、打亂順序的字母磚，磚的數量跟種類要**剛好等於這一關全部空格需要的正確字母**（不多給、不少給，例如某一關有 3 個空格分別要 B、O、S，字母區就剛好有這三個字母磚，順序打亂）。
4. **提示詞**：畫面下方顯示 `hintZh` 這段文字（例如「單字包括：床、地板、屋頂、門、沙發、房間喔！」），純文字提示，不是每個單字自己的個別線索——這點刻意比照使用者截圖的呈現方式（截圖裡的提示也是一段整體文字，不是逐字逐格的個別提示語）。

## 答題邏輯

- 使用者從字母區拖曳一個字母磚到某個空格上。
- 比對：這個字母磚的字母是否等於這個格子的正確答案（`crossword.schema.json` 資料裡已經隱含在網格座標中，App 端排版時就能算出每個格子的正確字母）。
- **答對**：字母磚放進格子，永久固定在那裡（玩家不能再拖走），字母區移除這個磚。
- **答錯**：字母磚彈回字母區原本的位置（可以搭配一個小小的「彈跳」CSS 動畫增加回饋感，不用做懲罰性的音效或文字，維持這個 App 一貫不強調挫折感的調性）。
- 全部空格都正確填滿＝這一關過關。

## 關卡機制

比照翻牌配對已經確立、使用者也熟悉的「一局玩三關」模式：**同一組單字內容玩三關，每一關「空格比例」遞增**，難度漸進：

- 第 1 關：約 40% 的格子是空格（其餘先給答案），例如 6 個單字共 15 個字母格，約留 6 格空白。
- 第 2 關：約 65% 空格。
- 第 3 關：約 85-90% 空格（幾乎全空，只留 1-2 格當提示錨點，避免完全沒有任何已知字母、變成無從下手的裸猜）。

挑選哪些格子當空格：在每一關開始時**隨機挑選**（同一關卡內容重玩會有不同的空格分佈，增加重玩價值），但要注意：交疊格（同時屬於兩個單字的格子）被挖空時，兩個單字都會受影響，這是正常且合理的，不用特別排除交疊格不能被挖空。

過三關的節奏跟畫面轉場，直接比照 `memoryMatchGame.ts` 的 `phase` 狀態機模式（`reveal`／`playing`／`levelComplete`／`complete` 這幾個階段的設計思路可以直接參考沿用，這裡不用重新發明一套機制）。

## 最高紀錄：星星評分（1-3 顆星）

使用者確認要用星星數表示成績。**評分依據建議用「總錯誤次數」（三關加總，越少越好）**，理由：這個 App 一貫刻意避免計時/时間壓力的設計（沒有倒數計時題型、慢速模式等等都在照顧不擅長快速反應的小朋友），用「拖錯幾次」當指標，跟小朋友的操作直覺一致，不會因為「還沒看清楚就被逼著快速拖曳」產生壓力，這點若使用者有不同想法歡迎再調整，但先照這個方向做。

星級門檻（可依實際試玩調整，先給一個合理預設）：
- 三關加總錯誤次數 0-2 次 → ⭐⭐⭐
- 3-5 次 → ⭐⭐
- 6 次以上 → ⭐

**建議順便把「遊戲最高紀錄」抽成一個共用模組**（這是遊戲室第二款遊戲了，值得現在就做這個小重構，避免以後每款遊戲各自寫一份高分紀錄邏輯）：

```ts
// app/src/gameHighScores.ts——遊戲室各遊戲共用的最高紀錄儲存，per-profile localStorage，
// 跟 gameTokens.ts／progress.ts 同一套模式。每款遊戲用自己的 gameId 當 key 的一部分，
```

`renderGameRoom()` 的每張遊戲卡片可以順便顯示 `getBestStars(profileId, game.id)`（沒玩過就不顯示星星，或顯示灰色空星），翻牌配對這款遊戲不強制補這個功能（維持它「純粹休閒獎勵、不記錄成績」的原始設計，除非使用者之後主動要求），但共用模組先做好，之後要加隨時可以接。

## 架構：獨立 iframe＋postMessage（比照翻牌配對遷移後的架構）

- 新增 Vite 進入點：`app/games/crossword.html` + `app/src/games/crosswordStandalone.ts`（`vite.config.ts` 的 `rollupOptions.input` 新增一行，比照 `memoryMatch` 那筆）。
- 引擎（不碰 DOM 的純邏輯 class）：`app/src/games/crosswordGame.ts`，负责：讀入 `Crossword` 資料（`row`／`col`／`direction`／`en`）→ 算出網格與每格正確字母 → 依關卡的空格比例隨機決定哪些格子是空格 → 提供 `dropLetter(cellId, letter)` 方法判斷對錯 → 追蹤錯誤次數、目前第幾關、全部完成時計算星等。
- 渲染（`crosswordStandalone.ts`）：網格 DOM、拖曳事件（HTML5 native drag-and-drop 或用 `pointerdown`/`pointermove`/`pointerup` 自己實作觸控相容的拖曳，**手機觸控相容性務必留意**——原生 HTML5 Drag and Drop API 在手機瀏覽器上支援度不好，這個 App 主要使用情境是手機，建議直接用 pointer event 自己做拖曳邏輯,不要依賴 `draggable` 屬性)、字母區排列、裝飾插圖、粉色系 CSS（`app/src/games/crosswordStandalone.css`，獨立於主站配色，比照翻牌配對遷移後每款遊戲有自己視覺風格的既有結論）。
- 沿用 `gameBridge.ts` 的訊息協定：`ready`／`requestReplay`／`exitToRoom`／`complete`（比照翻牌配對，遊戲進行中完全不用碰代幣，只有「再玩一次」需要問主站扣款）。
- `content/games/games.json` 新增一筆：

```json
{
  "id": "crossword",
  "name": "填字遊戲",
  "description": "拖曳字母填滿空格，找出隱藏在網格裡的英文單字。",
  "icon_placeholder": "🧩",
  "cost": 25,
  "status": "coming_soon",
  "order": 2
}
```

（我已經直接把這筆加進 `content/games/games.json` 了，消費代幣訂在比翻牌配對稍高的 25，因為關卡數/操作複雜度都比較高，這個數字之後可以依實際試玩調整。**`status` 我先設成 `"coming_soon"`**——遊戲室清單會顯示這款遊戲但標記「即將推出」、不能點擊，避免在引擎還沒做完之前，使用者點下去卻沒有對應的畫面。等 App 端完成實作、實機測試過拖曳/關卡/星等都正常，**記得把這筆的 `status` 改回 `"active"`** 才會正式開放遊玩，這是這次很容易忘記的最後一步。）

## 驗證

- 新增 `verify-crossword-logic.ts`（比照 `verify-memory-match-logic.ts`）：網格建構正確（交疊格字母一致）、`dropLetter()` 對錯判斷正確、空格比例依關卡遞增、錯誤次數正確累計、星等門檻計算正確、全部關卡完成觸發 `onComplete`。
- 新增 `verify-crossword-content.ts`（比照專案裡其餘內容驗證腳本的手法）：讀取 `content/crosswords/*.json`，驗證每個檔案符合 `crossword.schema.json`，且**用程式重新排版驗證所有單字交疊處字母一致**（跟我離線驗證用的同一種邏輯，確保content本身沒有排版錯誤，這是最容易出錯也最容易一次性用程式徹底排除的環節）、每個 `vocabId` 都能在對應主題的 `content/vocab/<topicFileKey>.json` 裡找到。
- `verify-game-bridge-messages.ts`（翻牌配對遷移時新增的那支）比照擴充，涵蓋填字遊戲的 `requestReplay` 分支也正確接到 `spendTokens`。
- `npm run build` 要過；因為拖曳互動、觸控相容性沒辦法在無瀏覽器環境驗證，務必實機（手機觸控＋電腦滑鼠兩種都要測）確認拖曳流暢、答錯彈回的動畫沒有卡頓、粉色系視覺跟裝飾插圖排版正常。

## 這次刻意不做的事

- 只做「居家空間」這一個主題打樣，不要順便多排幾個主題的關卡——使用者明確要求先做 1 個主題驗證整套機制。
- 不做「依使用者個人學習進度即時生成」的動態排版——已確認技術上不可靠，改用預先排版好的固定關卡。
- 不用調整代幣消費（25）跟星等門檻（0-2/3-5/6+）這些數字的實際手感，先照文件上線，之後有實際試玩回饋再回頭調整。
