# 任務：兒童英語學習平台 Phase 1 技術架構決策 + 最小可行骨架

你現在接手的是「兒童英語學習平台」專案的實際開發工作。這個專案已經完成產品規劃階段，你不需要重新設計產品功能，你的任務是把它蓋出來。

## 先讀這些（了解專案全貌，不用問我就能查到）
1. `HANDOFF.md` — 專案交接文件，進度總結、待決定的技術事項都在這
2. `docs/content-plan.md`（原檔名 `content-plan-gept-kids.md`） — 課程內容的資料結構與關卡分類邏輯
3. `content/schema/`、`content/vocab/`、`content/sentences/`、`content/passages/` — 已經做好的三個主題範例內容（Family／Colors／Animals & insects）與 Unit 0，直接可用，**不要更改資料結構**
4. `dashboard.html` — 目前專案進度快照

## 範圍界線（請嚴格遵守，不要自行擴大範圍）
- 只做 Phase 1：文字型題型（配對／排序／填空／選擇）＋ 基本登入登出／課程範圍／成效追蹤
- **不要**做口說題型、不要碰語音辨識——這是 Phase 4，故意延後
- **不要**做教師角色、家長帳號綁定、班級排行榜——這些已經確認不需要
- 目標使用者是家庭/個人本機使用，最終會上架到 GitHub（很可能是純靜態網站／GitHub Pages 型態），先不用考慮多人連線、雲端同步

## 第一個任務：技術選型 + 一條龍可跑通的最小骨架
1. 提出前端技術棧建議（框架／不用框架、要不要 TypeScript、進度資料怎麼存——例如純前端 + localStorage 可能就夠，不一定需要後端資料庫），簡短列出 2-3 個選項的優缺點，**跟我確認後再動工**，不要自己直接下決定。
2. 決定後，初始化專案骨架（開發用資料夾建議跟 content/、docs/ 分開，例如 app/ 或 src/），並準備好之後能乾淨地放上 GitHub（.gitignore、基本 README 骨架即可，不用現在就寫完整 README）。
3. 做出一個最小可行流程：讀取 `content/vocab/family.json`，實作「單字配對」這一種題型，讓 Family 主題可以在瀏覽器裡完整跑一輪（看到單字、配對、答對答錯回饋）。這一步的目的是驗證整條資料串接與技術選型可行，不用先做其他三種題型或其他主題。
4. 完成後跟我回報：技術選型理由、目前骨架長什麼樣子、下一步建議先做排序/填空/選擇哪一種題型比較合理。

如果過程中發現 content/ 裡的資料格式有不好用或缺欄位的地方，請先跟我確認要不要調整 schema，不要自己直接改。
